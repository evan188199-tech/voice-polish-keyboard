# Private reference integration boundaries

The current UI supports user-selected local JSON under a demo account. Preview and material selection are bound to the current in-memory account and generation; a replacement preview, account switch or revocation invalidates prior permits. Only selected fields and confirmed terms enter the local index. No production account or real Notion source is configured.

The main app contains an opt-in protected local index: the iOS storage implementation uses a per-scope AES-GCM key in device-only Keychain, encrypted app-container files, complete file protection and backup exclusion. Explicit save/load and deletion are wired to the prototype view. Scope is currently an account plus a single aggregated user-selected local-index identifier; it does not retain per-file provenance. Switching accounts clears the active in-memory view but keeps separately saved account-scoped data. Explicit revocation attempts key and file deletion; failure is reported, and must be retried. iOS compilation, Keychain, protection classes, backup behavior, failure recovery and multi-scene concurrency have not been verified. Tests inject an in-memory store and are not cryptographic or device validation.

`NotionPrivatePreviewReader` implements explicitly selected property filtering, paging, bounded retry and fail-closed permission/error handling. `NotionHTTPTransport` can be configured with an injected authorized credential provider, uses the official HTTPS endpoint and blocks redirects; no credential provider, source-selection UI, OAuth flow or production connection is configured. Test responses are fictional. Real source schema, property pagination, selected source authorization, token storage and customer-facing material rights still need separate review and device tests. Reader output is a preview: it is never automatically imported or published.

Keyboard UI and `PrivateReferenceSearchModel` support scoped searches and explicit selection when supplied an authenticated, short-lived snapshot. `PrivateSnapshotPublisher` projects only explicitly selected IDs and denies all peers by default. The production keyboard uses the disabled transport. Neither this protocol nor a test verifier establishes peer identity; existing TCP uses a publicly derivable build token and is not an authenticated private-data channel. No private index, credential, link or image is sent over that bridge. A real peer-verification mechanism and revocation/invalidation behavior must be implemented and verified before enabling it; no App Group or Keychain sharing entitlement is assumed.

The app also offers explicit local-only expiring clipboard copies and the system share sheet. These are user actions, not messages sent or proof that a recipient can access a file. Copied text carries a transient-private pasteboard type, and the keyboard sampling path checks that type before reading to avoid adding these copies to clipboard history. Fake-pasteboard tests do not prove type preservation across real iOS processes or other applications; the marker cannot remove existing history or protect content copied again by another app. Images remain demo placeholders, not fetched assets.

Before real use: explicitly authorize the selected account and specific sources using a supported least-privilege flow; independently verify each customer-facing link and image, channel, expiry and attribution; validate protected local storage, source-specific provenance, secure keyboard transport and revocation; then test iOS behavior across hosts. Readable source pages are not proof of customer file access. Never put private content, source URLs, credentials or tokens into code, fixtures, logs or public issue discussion.
